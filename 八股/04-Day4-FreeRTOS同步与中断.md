## Q10 函数指针与回调

函数指针保存一个可调用函数的地址；回调是把函数交给其他模块，让对方在事件发生时调用的一种组织方式。

```c
typedef void (*sample_cb_t)(int value, void *ctx);

struct Sensor {
    sample_cb_t callback;
    void *context;
};

void sensor_publish(struct Sensor *s, int value)
{
    if (s != NULL && s->callback != NULL) {
        s->callback(value, s->context);
    }
}
```

`void (*fp)(int)` 是函数指针；`void *fp(int)` 是一个返回 void 指针的函数声明，括号不能少。调用时函数类型必须匹配，强转不兼容函数指针后调用不能保证正确。

ctx 用于带回设备对象、队列句柄等状态。注册后，ctx 指向的对象必须活得足够久；不能把即将返回函数的局部变量地址留给异步回调。注销回调还要考虑“注销时是否有一次回调正在执行”。

### 回调里能不能耗时

回调本身没有“天生在中断/线程里”的属性，**由调用它的人决定上下文**。

| 调用上下文 | 适合做什么 | 应避免什么 |
|---|---|---|
| ISR/DMA 完成中断 | 读取必要状态，投递短事件 | 阻塞、长日志、网络发送 |
| FreeRTOS 定时器服务任务 | 短计算，非阻塞通知工作任务 | 等信号量、延时、长 I/O |
| 网络/BLE 协议栈事件任务 | 快速保存信息、投递消息 | 长时间占住协议栈任务 |
| 专门的业务工作任务 | 可在预算内执行处理 | 无上限阻塞、持锁等待网络 |

“我在哪用过”只能按真实经历回答。可用模板：“【驱动/模块】注册【回调】，它在【真实上下文】执行；回调只做【短操作】，将【数据或事件】交给【任务】，并处理【队列满/对象生命周期】。”

## Q22 优先级反转、继承与天花板

设 H 高、M 中、L 低。L 持有资源锁；H 想拿锁而阻塞；M 不用这个锁但一直运行，导致 L 迟迟无法释放锁，H 被 M 间接拖住。这就是典型的优先级反转。

```text
L 获锁 → H 请求锁并阻塞 → M 抢占 L → L 无法解锁 → H 继续等待
```

### 优先级继承

支持继承的互斥量发现 H 在等 L，就临时提升 L 的有效优先级，使 M 不能继续压住 L。L 尽快运行到解锁，H 获得锁继续工作。

继承缩短中优先级任务造成的额外阻塞，不消除 L 持锁操作本身的时间，也不能解决死锁、无限阻塞或错误持锁。多个互斥量嵌套会更复杂；FreeRTOS 使用简化的继承机制，不能宣称具备任意嵌套场景下的完整最优恢复行为。[FreeRTOS mutex 说明](https://freertos.org/Real-time-embedded-RTOS-mutexes.html)

### 优先级天花板

预先为资源指定可能访问它的任务中的最高优先级。以**立即天花板协议**为例，任务获锁后立即提升到资源天花板，而不必等高优先级任务实际被阻塞。原始优先级天花板协议还有系统天花板和准入规则；两种不要混成一句话。

合理的天花板协议在其假设满足时可以限制阻塞并避免某些死锁，但需要完整资源使用关系与协议实现。普通 FreeRTOS mutex 默认提供继承，不提供一套通用的优先级天花板协议；不能随意手动提优先级就声称完整实现了它。

工程措施往往更直接：缩短持锁时间、统一加锁顺序、不持锁做网络/Flash 长操作，或把外设交给一个服务任务串行访问。

## Q23 三种同步工具怎么选

| 工具 | 主要含义 | 数据/状态 | 典型场景 |
|---|---|---|---|
| 队列 | 传递消息 | 固定长度条目，通常复制条目内容 | 传感器样本、命令、事件 |
| 二值信号量 | 有/无一个待处理通知 | 0 或 1，重复 give 可能合并/失败 | ISR 通知任务某状态需要处理 |
| 计数信号量 | 计数/资源数量 | 0～最大计数 | 资源池、计数事件；达到上限也会丢计数 |
| 互斥量 | 资源独占所有权 | 持有者及继承相关状态 | 多任务共享 I2C、数据结构 |
| 任务通知 | 直接通知某一个任务 | 通知状态/值，取决于 API 模式 | 一对一唤醒、位标志、事件计数 |

队列“传指针”时复制的只是指针值，并不会自动深复制其指向的数据。因此必须规定缓冲区何时可复用、谁归还内存池。小消息按值复制更简单；大块数据常用池块指针，减少复制开销。

### 内部是否相同

FreeRTOS 的队列、传统信号量和互斥量复用了 `queue.c` 中许多基础设施，但语义和元数据不同：

- 队列需要数据存储、读写位置、当前条目数及等待发送/接收的任务列表。
- 信号量可看作零长度条目的计数对象；二值信号量最大计数为 1。
- 互斥量还跟踪持有任务，并处理优先级继承；递归互斥量另有递归次数。
- 任务通知状态和值位于目标任务 TCB，不等于另建一个普通队列。

共用实现不意味着可以互相替换。等待队列空位、等待信号量和等待锁分别表达不同的业务关系。

## Q24 二值信号量不等于互斥量

| 项目 | 二值信号量 | 互斥量 |
|---|---|---|
| 所有者 | 无任务所有权要求，可由一个执行者 give、另一个 take | 由持有任务按规则释放 |
| 优先级继承 | 无 | 有简化的优先级继承 |
| ISR | 对应 FromISR 接口可用于允许调用内核 API 的中断 | 不能在 ISR 中获取/释放 mutex |
| 意义 | 事件通知/同步 | 资源排他保护 |

用二值信号量保护 I2C 可能丢失优先级继承，增加反转风险；用 mutex 从 ISR 通知任务则违反互斥量的任务所有权语义。

现代 `xSemaphoreCreateBinary()` 创建后初始为空；创建 mutex 后一般初始可获取。不要把旧宏 `vSemaphoreCreateBinary` 的行为与新创建函数混淆。任务通知通常适合替代简单的一对一二值通知，但要选对通知动作和清除规则。

## Q25 为什么要有 FromISR

普通任务 API 可能导致当前任务阻塞、使用任务上下文的临界区方式或执行调度路径。ISR 不是一个可以放到阻塞队列里等待的任务；阻塞还可能等待必须由当前中断返回后才能执行的代码，形成死锁。

FromISR 版本采用 ISR 适用的内核访问方式，不带普通阻塞等待；通过 `pxHigherPriorityTaskWoken` 等参数告诉调用者是否需要在退出中断时请求调度。

```c
/* 示意：常见 Cortex-M FreeRTOS 移植；硬件函数需由工程提供。 */
void DEVICE_IRQHandler(void)
{
    BaseType_t higher_woken = pdFALSE;
    uint32_t sample = read_and_ack_device_irq();

    if (xQueueSendFromISR(sample_queue, &sample, &higher_woken) != pdPASS) {
        /* 按预设策略丢弃/覆盖/标记溢出，不能在这里等待空位。 */
    }
    portYIELD_FROM_ISR(higher_woken);
}
```

这个示例要求队列已创建，条目大小为 `sizeof(uint32_t)`，且中断优先级允许调用内核。`portYIELD_FROM_ISR` 的名字/形式依移植而异，不能未经核对复制到所有平台。

### 不是每个中断都能调用 FromISR

在使用 BASEPRI 的 Cortex-M 移植中，能调用内核的 ISR 必须处于允许的优先级范围。数值越小，中断紧急程度越高；比 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 阈值更紧急的 ISR 不得调用这些内核 API。

举例：假设使用未移位的逻辑优先级 0～15，库级 syscall 阈值为 5，则通常 5～15 可调用，0～4 不可调用。具体要核对实现的优先级位数、分组和宏是否已左移；不能把库级数值和寄存器编码混用。优先级 0 尤其不能随意调用内核 API。

## Q26 中断里为什么要短

ISR 越长，就越可能推迟同级/低紧急度中断和任务处理，导致串口 FIFO 溢出、采样抖动、协议超时。高频 ISR 即便单次不算长，累计 CPU 占用也可能很大。

普通 printf 通常不适合 ISR，因为它可能格式化耗时、占较多栈、获取 libc/UART 锁、等待缓冲或 UART 完成。如果等待的 UART 中断不能运行，甚至可能死锁。

“ISR 中任何情况下都不能输出字符”过于绝对：专门设计的无锁、非阻塞、时间有界 trace 可以使用；需要核对实现。正常项目优先把时间戳和事件码写入预分配环形缓冲，再由日志任务格式化输出。

建议结构：ISR 清源、记录必要数据、通知任务；任务做解析、滤波、打印和上传。测量手段是 GPIO 翻转加逻辑分析仪，或合适的周期计数器；记录最长持续时间与事件丢失计数。

## Q27 临界区怎么实现

临界区保护很短的共享状态更新，不能把整个业务流程包进去。

| 平台/方式 | 实现思路 | 不能误解为 |
|---|---|---|
| 常见 Cortex-M3/M4 FreeRTOS | 提高 BASEPRI 屏蔽阈值，屏蔽允许调用内核的那部分中断，支持嵌套 | 所有中断都彻底关闭 |
| 某些 Cortex-M0 移植 | 常使用 PRIMASK 等更粗粒度屏蔽 | 与 M4 的优先级阈值完全一样 |
| ESP-IDF SMP | 本核中断控制配合自旋锁保护跨核共享状态 | 只关本核中断就能保护另一核 |
| 仅挂起调度器 | 暂停任务调度的某些行为 | 禁止 ISR 修改数据，或通用跨核锁 |

高紧急度且未被 BASEPRI 屏蔽的 ISR 仍能执行，故不能让它随便修改“只受此临界区保护”的数据。[Cortex-M 移植实现](https://raw.githubusercontent.com/FreeRTOS/FreeRTOS-Kernel/main/portable/GCC/ARM_CM4F/port.c)；[ESP-IDF 多核临界区说明](https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32/api-reference/system/freertos_idf.html)

```c
/* 单核 FreeRTOS 示意：只保护短小的读改写 */
taskENTER_CRITICAL();
local = shared_count;
shared_count = 0;
taskEXIT_CRITICAL();
process_count(local);  /* 长处理放外面 */
```

进入/退出需正确配对，ISR 使用对应 ISR 版本并恢复原屏蔽状态。临界区内不做阻塞 API、printf、网络收发、Flash 擦写。扩大关中断范围会增加最坏中断延迟，还可能触发中断看门狗；它与 mutex 的任务阻塞式保护不同。

## Q28 软件定时器与硬件定时器

| 项目 | FreeRTOS 软件定时器 | MCU 硬件定时器 |
|---|---|---|
| 时间基础 | 内核 tick，通常还受服务任务调度影响 | 外设计数器/时钟 |
| 回调执行 | 定时器服务任务 | 常见为 ISR，也可能由驱动再转交任务 |
| 适合 | 心跳检查、状态超时、周期性轻量通知 | PWM、输入捕获、精密触发、短周期计时 |
| 主要限制 | tick 分辨率、服务任务忙、命令队列延迟 | 定时器数量、时钟精度、ISR 延迟 |

多个 FreeRTOS 软件定时器共用服务任务：一个回调阻塞，就会拖住其他定时器及命令处理。**回调不能调用会阻塞的操作**，如 `vTaskDelay`、长时间 take，或对满队列等待。若在回调中调用向定时器命令队列发送请求的 API，应使用零阻塞时间并检查失败。[FreeRTOS 软件定时器说明](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/05-Software-timers/01-Software-timers)

```c
/* FreeRTOS 软件定时器回调示意 */
static void heartbeat_timer_cb(TimerHandle_t timer)
{
    (void)timer;
    xTaskNotifyGive(worker_task);  /* 快速通知；工作在 worker 中完成 */
}
```

硬件 PWM 可以不靠每次 ISR 就维持准确边沿；硬件定时器“比较事件精确”也不意味着 ISR 软件处理没有延迟。ESP-IDF 的 `esp_timer` 是另一套设施，不能把所有 FreeRTOS 软件定时器结论逐字套到它的每种分发模式。

## 综合练习：采样链路

设计目标：采样 ISR 每 1ms 到来，处理任务偶尔忙 10ms，每条样本 4B。

1. 如果必须保留每条样本，二值信号量够吗？
2. 队列容量至少如何估算？
3. 队列满后怎么处理？
4. 上传任务每次可能等网络 2 秒，是否与采样共用一个锁？

> [!answer]- 参考方案
> 1. 不够，事件会合并；使用队列或环形缓冲，通知只负责唤醒。2. 10ms 已积累约 10 条，还要加边界相位、突发与余量，例如先取 16 再验证，且长期平均消费必须快于产生。3. 明确丢新/丢旧/降采样策略并统计溢出，不能静默。4. 不应持采样资源锁等待网络，使用独立消息/缓冲所有权传递。

## 自测与答案

1. L 持锁被 M 抢占，H 等锁，继承提升谁？
2. 队列传了指针，发送任务能马上释放数据吗？
3. 高紧急度 ISR 用 FromISR 就一定合法？
4. 软件定时器回调能等 100ms 信号量吗？
5. `vTaskSuspendAll()` 能保护与 ISR 共享的数据吗？

> [!answer]- 答案
> 1. 提升锁持有者 L。2. 不能，须按所有权约定保证接收方使用期间有效。3. 不能，仍受内核允许中断优先级范围限制。4. 不能，会阻塞服务任务。5. 不能，它不等同于屏蔽中断。
