## Q04 结构体对齐与重排

CPU/总线通常更适合访问特定边界上的数据，ABI 会规定类型的对齐要求。对齐不是“所有成员都按 4 字节排”，也不是“32 位机器的所有类型都占 4 字节”。

**常见自然对齐的手算步骤：**

1. 当前偏移从 0 开始。
2. 把偏移向上取整到当前字段对齐值的倍数，作为该字段起始位置。
3. 加上字段大小，继续下一个字段。
4. 结构体对齐通常取成员对齐的最大值；最终总大小向上取整到这个值的倍数。

对齐取整公式：`align_up(x, a) = ((x + a - 1) / a) * a`。实际 C 计算要考虑整数溢出；这里只用于小尺寸手算。

### 完整算例

假设 `uint8_t` 大小/对齐 1，`uint16_t` 为 2/2，`uint32_t` 为 4/4；没有 packed、特殊对齐属性或 ABI 例外：

```c
struct Sample {
    uint8_t  flag;
    uint32_t timestamp;
    uint16_t value;
    uint8_t  status;
};
```

| 字段 | 对齐 | 起始偏移 | 占用字节 | 原因 |
|---|---:|---:|---|---|
| flag | 1 | 0 | 0 | 从 0 开始 |
| 填充 | — | 1 | 1～3 | 为下一个字段补到 4 的倍数 |
| timestamp | 4 | 4 | 4～7 | 满足 4 字节对齐 |
| value | 2 | 8 | 8～9 | 已满足 2 字节对齐 |
| status | 1 | 10 | 10 | 无需额外对齐 |
| 尾部填充 | — | 11 | 11 | 总大小补到 4 的倍数 |

所以 `sizeof(struct Sample) = 12`，对齐为 4。尾部填充保证数组中下一个元素里的 timestamp 仍正确对齐。

重排：

```c
struct SampleCompact {
    uint32_t timestamp;  /* 0～3 */
    uint16_t value;      /* 4～5 */
    uint8_t  flag;       /* 6 */
    uint8_t  status;     /* 7 */
};                      /* 大小 8，对齐 4 */
```

1000 个元素由 12000 字节降至 8000 字节。按对齐从大到小排列是常用启发式，不是所有复杂结构都最优；也要考虑访问局部性、ABI 兼容性和外部存储格式。

### packed 为什么不是万能办法

packed 可以改变填充，却可能导致未对齐访问，造成额外指令、性能下降，甚至某些处理器上的异常。取 packed 成员地址后传给要求自然对齐的函数尤其危险。它也不解决字节序、位域顺序和协议版本问题。

不要直接把结构体内存发到网络：padding 内容可能不确定、泄露旧数据，大小和布局也未必一致。也不要用 `memcmp` 一概判断两个结构体的逻辑字段相等。

用 `sizeof`、`_Alignof`、`offsetof` 和编译期断言验证本平台；本练习的完整代码见 `实验代码/02_layout.c`。结构体及位域布局受 ABI 影响。[GCC 实现说明](https://gcc.gnu.org/onlinedocs/gcc/Structures-unions-enumerations-and-bit-fields-implementation.html)

## Q05 结构体与联合体

| 项目         | struct            | union            |
| ---------- | ----------------- | ---------------- |
| 成员存储       | 各自有独立位置，通常依声明次序排列 | 从同一起始地址共享存储      |
| 同时保存多个成员的值 | 可以                | 通常只能把一个成员当作当前有效值 |
| 大小         | 成员加内部/尾部填充        | 至少容纳最大成员，再满足对齐要求 |
| 典型用途       | 设备状态、消息、配置        | 多种互斥消息载荷共用空间     |

```c
enum EventKind { EVENT_VALUE, EVENT_ERROR };

struct Event {
    enum EventKind kind;
    union {
        struct { uint16_t channel; uint16_t value; } sample;
        uint32_t error_code;
    } payload;
};
```

这是“标签 + 联合体”：先看 kind，再访问对应 payload。适合事件队列，同一事件要么是采样，要么是错误，不必为两种载荷同时留独立空间。注意枚举大小依实现，不能不经测量就断言整个 Event 必为 8 字节。

联合体也常用于寄存器视图、字节视图。但在 C 中写一个成员再读取另一个成员会涉及对象表示、可能的陷阱表示与实现细节，不能当成可移植的协议转换方案；C++ 规则又不同。查看原始字节优先使用 `unsigned char *`，同尺寸对象表示复制可用 `memcpy`，但 memcpy 本身不会转换字节序。

## Q06 位域与跨字节解析

位域用冒号声明字段位宽：

```c
struct Flags {
    unsigned int enabled : 1;
    unsigned int mode    : 3;
    unsigned int error   : 4;
};
```

enabled 可表示 0～1，mode 可表示 0～7。代码看起来与协议字段很接近，所以历史代码、固定编译器的寄存器映射中常见这种写法。

**不能由“1+3+4=8”推出 `sizeof(struct Flags)==1`。** 分配单元大小、位分配方向、是否跨存储单元由实现/ABI 决定；普通 `int` 位域的符号性也不能随意假设。位域不能单独取地址，不能对位域应用 sizeof。

“跨字节怎么排”的正确回答是：先看编译器和 ABI。C 没有规定通用的从低位向高位排列；**大小端也不能单独决定所有位域布局**。零宽匿名位域如 `unsigned int : 0;` 可要求后续位域进入下一个分配单元边界，但仍不等于指定网络字节位置。

### 可移植的跨字节解析

假设协议明确规定：先传高字节；16 位字中 bits[15:13] 是 type，bits[12:0] 是 value。

```c
uint16_t word = (uint16_t)(((uint16_t)buf[0] << 8) | buf[1]);
uint8_t type = (uint8_t)((word >> 13) & 0x07u);
uint16_t value = word & 0x1FFFu;
```

收到 `A1 23` 时，word 是 `0xA123`，type = 5，value = `0x0123` = 291。反向打包先验证 `type<=7` 且 `value<=8191`，再计算 `word=((uint16_t)type<<13)|value`，逐字节输出。

读 buf 前还必须验证至少有 2 字节。先提升为无符号的足够宽类型再移位，避免符号扩展、过宽移位等问题。

> [!warning] 协议与寄存器的两类风险
> 网络协议优先显式掩码/移位，不依赖本地位域布局。硬件寄存器还要防读改写副作用，例如写 1 清零（W1C）的寄存器，`reg |= mask` 可能误清其他位；应按手册直接写指定掩码或使用专用寄存器。

## Q07 malloc 与静态数组

先区分：`void f(void) { uint8_t buf[1024]; }` 是自动存储期局部数组，常占任务栈；文件级数组或函数内 `static uint8_t buf[1024];` 才有静态存储期。

| 方案 | 优点 | 风险/代价 | 常用场景 |
|---|---|---|---|
| 静态数组 | 容量与地址稳定，无运行期分配失败 | 固定占用，过大浪费；共享时要同步 | DMA 缓冲、固定采样队列、关键任务资源 |
| 自动局部数组 | 自动回收、调用间隔离 | 占栈，越界可能破坏返回地址；不能异步借用到返回后 | 小型临时数据 |
| malloc | 按需申请，适合可变长度/并发数量 | 失败、碎片、延迟变化、泄漏及生命周期复杂 | 有明确上限的非关键动态对象 |
| 固定块内存池 | 申请/归还可控、易统计 | 块内浪费，容量须预估 | 网络包、消息对象、实时路径 |

MCU 上我优先让关键路径的 RAM 用量可预测：初始化时一次分配，运行时使用静态缓冲或内存池。不是所有 malloc 都禁止，而是必须有上限、失败处理、所有权和延迟评估。

RTOS 静态创建接口通常由应用提供控制块及存储，例如 `xTaskCreateStatic`、`xQueueCreateStatic`；它们不意味着业务中不存在其他堆分配。网络/TLS 库也可能自行分配。

## Q08 内存碎片

**外部碎片**：空闲总量足够，但不连续，无法满足一次大申请。

```text
地址递增 →
[空闲 64B][占用 32B][空闲 64B][占用 32B][空闲 64B]
总空闲 192B，最大连续块 64B；申请 100B 仍可能失败。
```

**内部碎片**：已经分配的块中有空间没被有效使用。例如用 64B 池块装 50B 数据，块内浪费 14B，另有管理开销。

碎片和泄漏不同：泄漏是对象不再使用却未释放；碎片可在没有泄漏的情况下发生。嵌入式 RAM 少、常要求长期运行与有界响应，而且网络/OTA/TLS 的峰值内存需求可能很大，运行数天后才失败很难排查。

规避与观察：

1. 尽量不要把寿命很长和很短的对象交错分配在同一个堆。
2. 固定大小对象用池；变长对象可用多个尺寸等级，限制最大长度和数量。
3. 关键对象启动时一次分配；每次分配检查失败，定义降级/丢弃策略。
4. 记录总空闲量、历史最低空闲量、最大连续空闲块；仅看“还剩多少字节”不够。
5. 做长时间压力测试，混合正常、重连、OTA 和异常路径，而不只是循环申请同样大小。

原生 FreeRTOS 常见示例分配器：`heap_1` 只分配不释放；`heap_2` 可释放但不合并相邻空闲块；`heap_3` 包装标准 malloc/free；`heap_4` 合并相邻空闲块；`heap_5` 支持多个不连续区域并具备合并机制。合并相邻块只能缓解碎片，不能移动仍在使用的对象；因此 heap_4 并不“没有碎片”。ESP-IDF 的堆管理另有实现，不能直接套这张表。[FreeRTOS 内存管理说明](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/09-Memory-management/01-Memory-management)

## Q11 大小端与序列化

多字节数值 `0x12345678`，按内存地址从低到高：

| 字节序 | 内存字节 |
|---|---|
| 小端 | `78 56 34 12` |
| 大端 | `12 34 56 78` |

允许用字符类型查看对象表示：

```c
uint32_t x = 0x01020304u;
const unsigned char *p = (const unsigned char *)&x;
if (p[0] == 0x04) { /* 本机为常见小端表示 */ }
else if (p[0] == 0x01) { /* 本机为常见大端表示 */ }
```

网络协议中的标准整数通常用大端（网络字节序），但不是“所有自定义载荷天然都大端”；载荷格式必须双方约定。16/32 位可使用平台的 `htons/htonl`、`ntohs/ntohl`，或显式编码：

```c
void put_u32_be(uint8_t out[4], uint32_t v)
{
    out[0] = (uint8_t)(v >> 24);
    out[1] = (uint8_t)(v >> 16);
    out[2] = (uint8_t)(v >> 8);
    out[3] = (uint8_t)v;
}
```

不要直接用 `*(uint32_t *)&buf[1]` 解析，可能同时碰到未对齐、别名规则和字节序问题。字节序也不等于 SPI 的 MSB-first/LSB-first：前者谈多个字节的排列，后者谈一个传输字内位的发送顺序。

## Q13 SPI 时序与四种模式

常见四线 SPI：SCK 时钟、MOSI 主发从收、MISO 主收从发、CS 片选（常为低有效）；这里不计电源与地。主设备提供时钟，每个时钟周期通常同时移入/移出一位。即使只读取，主设备也常要发送 dummy 数据产生时钟。

CPOL 决定 SCK 空闲电平。CPHA=0 在第一个边沿采样，CPHA=1 在第二个边沿采样。“第一个边沿”由空闲电平决定，不一定是上升沿。

| 模式 | CPOL | CPHA | 空闲电平 | 采样边沿 | 常规数据更新边沿 |
|---|---:|---:|---|---|---|
| 0 | 0 | 0 | 低 | 上升沿（第一沿） | 下降沿 |
| 1 | 0 | 1 | 低 | 下降沿（第二沿） | 上升沿 |
| 2 | 1 | 0 | 高 | 下降沿（第一沿） | 上升沿 |
| 3 | 1 | 1 | 高 | 上升沿（第二沿） | 下降沿 |

CPHA=0 时第一位必须在第一个采样沿之前就稳定；不能等到第一个采样沿才开始输出。四模式的定义可对照 [Analog Devices SPI 时序说明](https://www.analog.com/en/resources/design-notes/interfacing-spi-realtime-clocks-rtcs-with-a-microcontroller.html)。

模式 0 的一字节读取思路：

```text
CS  拉低 → 满足片选建立时间 → 产生 8 个时钟 → 满足片选保持时间 → CS 拉高
每个上升沿：双方采样；每个下降沿：为下一位更新数据。
```

真实读寄存器往往是 `命令 + 地址 + dummy clocks + 数据`，CS 要覆盖整个事务。命令中的读写位、地址递增方式、dummy 数量、最大 SCK、建立/保持时间全部以从设备手册为准。

调试顺序：确认电压/接线/共地 → CS 和时钟空闲电平 → 模式和位序 → 降低频率 → 检查命令/地址 → 测试固定 ID 寄存器 → 检查 DMA 缓冲与事务边界。波形有跳变不代表采样正确。

> “我接的是【真实器件】，手册规定【模式、最大频率、命令格式】。我配置【实际参数】，用读取【ID/状态寄存器】验证，再用逻辑分析仪检查 CS 和采样沿。”方括号必须填写自己的真实记录。

## Q14 SPI 与 I2C 怎么选

| 项目 | 常规 SPI | 常规 I2C |
|---|---|---|
| 信号线 | 单从设备常见 4 根，多从设备通常共享 3 根数据/时钟线，各有 CS | SDA、SCL 两根共享线 |
| 电气 | 常见推挽，未选中从设备的 MISO 应释放 | 开漏/开集，需要合适上拉 |
| 寻址 | 常用 CS 选择，无统一地址协议 | 常见 7 位地址，也有 10 位地址 |
| 双向 | 可全双工 | SDA 上分时双向，通常称半双工 |
| 速率 | 无统一固定上限，常见 MHz 到数十 MHz，取决于双方和布线 | 常用 100k/400kbit/s；Fm+ 1M、Hs 3.4Mbit/s 需双方支持 |
| 协议机制 | 基础 SPI 无统一 ACK/重试/帧格式 | 有 ACK/NACK、仲裁；部分设备支持时钟拉伸 |
| 典型选择 | 显示屏、高吞吐 ADC、Flash | 多个低速传感器、RTC、小配置器件 |

I2C 还有 5Mbit/s 的单向 Ultra Fast-mode，不应把它当成普通双向 I2C 的直接提速档。[NXP I2C 总线规范](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf?fsrch=1&pageNum=1&sr=3)

典型 I2C 寄存器读：`START → 地址+写 → ACK → 寄存器地址 → ACK → 重复START → 地址+读 → 数据 → 主机ACK（还要读）/NACK（最后字节）→ STOP`。

SCL 高电平时 SDA 从高变低是 START，从低变高是 STOP；普通数据在 SCL 高时保持稳定。每字节 8 位后还有 ACK 位，所以“400 kbit/s”不是每秒 50KB 的净业务吞吐。总线电容和上拉影响上升时间，不能只把软件分频调快。

选型还要考虑引脚、设备数量/地址冲突、线长、电磁环境、功耗和驱动支持。两者通常都是板级短距离总线；不能仅因“线少”就认为 I2C 适合任意长线。
