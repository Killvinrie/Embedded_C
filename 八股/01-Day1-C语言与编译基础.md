## Q01 volatile 到底保证什么

`volatile` 告诉编译器：这个对象的访问有外部意义，必须按照该实现对 volatile 的约定保留必要的访问。典型对象是内存映射寄存器，以及在目标工具链约定下被 ISR 异步修改、被主循环读取的变量。

它解决的是**编译器对访问的优化问题**，不等于“每次直接读物理 RAM”，也不保证原子性、线程同步、缓存一致性或普通内存的访问顺序。[GCC 对 volatile 的说明](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html)

### 不加时，轮询可能怎么优化

以下是 MCU 思路示例；ISR 的声明、向量表和清标志方法由平台决定：

```c
static volatile unsigned int ready;

void device_irq_handler(void)
{
    /* 按芯片手册清除硬件中断源。 */
    ready = 1;
}

void wait_ready(void)
{
    while (ready == 0) {
        /* 等待 ISR。 */
    }
}
```

若去掉 volatile，编译器==🔴分析当前执行流==时可能看不到 `ready` 被修改，于是把循环改成类似下面的逻辑：

```c
unsigned int cached = ready;  /* 只加载一次 */
if (cached == 0) {
    for (;;) { }             /* 再也不读 ready */
}
```

这是**可能的优化**，不代表所有编译器、所有优化等级都一定如此。`-O0` 能运行不能证明代码正确。实验使用 `-O2 -S` 查看实际生成的加载位置；不要在普通电脑程序里假装有 ISR 并运行这个死循环。

### “中断标志一定要加”该怎样精确回答

当主循环通过普通 C 访问轮询一个由 ISR 异步更新的对象，且工具链要求用 volatile 表达这种访问时，应加上。若已经用符合平台约定的原子操作、驱动访问器或 RTOS 通知来同步，就不能再一概说所有中断相关变量必须手写 volatile。

更关键的是：**加了仍然可能丢事件。**

```c
if (ready) {
    ready = 0;
    handle_event();
}
```

若 ISR 在 `if` 判断后、清零前再次写入 1，这次事件会被清掉。二值标志本来就只能表示“至少发生过一次”，不能记录事件次数。需要逐次计数时考虑计数信号量、任务通知计数或队列；需要“读取并清除”一致性时使用适当临界区/原子操作。

### 三个常见误区

| 说法                                                   | 正确理解                                            |
| ---------------------------------------------------- | ----------------------------------------------- |
| `volatile count++` 是原子的                              | `++` 通常是读、加、写；两个执行者可能覆盖更新                       |
| `data = x; ready = 1;` 中 ready 是 volatile，所以能发布 data | 普通数据与 volatile 访问没有这种通用同步保证；多线程应用需同步原语/合适的原子内存序 |
| DMA 缓冲区加 volatile 就行                                 | 还要考虑缓存清理/失效、内存屏障、对齐及 DMA 内存区域限制，按芯片/驱动要求处理      |

内存映射寄存器常写成 `volatile uint32_t *`；若硬件可修改、软件只能读，可用 `const volatile uint32_t *`。寄存器地址和访问宽度必须来自芯片手册，不能随意编造地址运行。

> [!tip] 面试回答
> volatile 用来保留对外部可变对象的必要访问。ISR 修改而主循环轮询的标志通常需要它，否则加载可能被移出循环。但它不解决原子性和事件丢失；RTOS 中我优先用任务通知或队列建立同步。

## Q02 static、作用域、存储期和链接性

先分清三个问题：**作用域**是名字在哪里可见；**存储期**是对象存在多久；**链接性**是不同声明能否指向同一个实体。把这三个混为一谈，会把 static 讲错。

| 写法 | 名字作用域 | 存储期/效果 | 链接性 |
|---|---|---|---|
| 函数内 `int n;` | 所在块 | 自动存储期，执行到所在块时存在 | 无 |
| 函数内 `static int n;` | 仍是所在块 | 静态存储期，整个程序运行期间存在，保留上次值 | 无 |
| 文件级 `int n;` | 文件作用域 | 本来就是静态存储期 | 通常外部链接 |
| 文件级 `static int n;` | 文件作用域 | 仍是静态存储期 | 内部链接，只供本翻译单元引用 |
| 文件级 `static void f(void);` | 文件作用域 | 函数只在本翻译单元内链接；不按局部变量谈生命周期 | 内部链接 |

“本文件”更严谨地说是**翻译单元**：一个 `.c` 加上经预处理展开的头文件内容。

```c
unsigned int next_id(void)
{
    static unsigned int id;  /* 未显式初始化时为 0 */
    return ++id;
}
```

连续调用返回 1、2、3。`id` 没有因此变成所有函数可见的全局名字；它也不是每次进入函数重新初始化。C 中静态存储期对象的初始化规则不同于 C++ 局部静态对象的动态初始化，不能直接照搬 C++ 的“首次调用自动线程安全初始化”说法。

局部 static 被多任务共享时仍要同步；它可能破坏函数的可重入性。例如多个任务调用上面的函数，`++id` 可能竞争。

常见 MCU 链接布局：已初始化且可写的全局/static 对象通常在 `.data`，启动时由 Flash 中的初值复制到 RAM；零初始化对象通常在 `.bss`，启动时清零；只读数据常放 `.rodata`。这些由链接脚本和工具链决定，**不是 static 关键字承诺的物理位置**。

> [!tip] 面试回答
> 局部 static 改变存储期，作用域仍在块内；文件级 static 主要把链接性改为内部链接，全局对象的存储期原本就贯穿程序；static 函数用于模块内部封装。

## Q03 const 与指针

从变量名向外读，把 `*` 两侧分清。

| 声明 | 指针本身能改吗 | 能通过这个指针改对象吗 |
|---|---|---|
| `int *p` | 可以 | 可以 |
| `const int *p` | 可以 | 不可以 |
| `int const *p` | 可以，与上一行相同 | 不可以 |
| `int * const p = &a` | 不可以 | 可以 |
| `const int * const p = &a` | 不可以 | 不可以 |

```c
int a = 10, b = 20;
const int *p = &a;
p = &b;       /* 合法：改指向 */
/* *p = 30;   不合法：不能通过 p 修改 */

int * const q = &a;
*q = 30;      /* 合法：改 a */
/* q = &b;    不合法：q 自身 const */
```

### ==🔴const 的对象真的不能改吗

必须区分“对象本来被定义成 const”和“访问路径带 const”。

```c
int a = 1;
const int *view = &a;
a = 2;                    /* 合法，a 本来可写 */
int *back = (int *)view;
*back = 3;                /* 此例合法：最终对象确实是可写的 int */

const int fixed = 1;
/* *(int *)&fixed = 2; */ /* 未定义行为，不能以运行结果证明合法 */
```

const 不承诺一定在 Flash，也不承诺必定有实际内存单元。编译器可能常量传播；链接器也可能把只读对象放入受保护区域。强制转换只是绕开类型检查，不能把真正的 const 对象变成可合法修改的对象。

补充两处高频陷阱：

- C 的 `const int n = 8;` 一般不是整数常量表达式；需要 `case` 标签等场景时可用枚举常量/宏。C 与 C++ 不完全相同。
- `int **` 不能直接安全地转换成 `const int **`。如果允许，函数就能通过第二级指针把真正的 const 对象塞给一个 `int *`，破坏类型安全。

接口中常见 `void send_bytes(const uint8_t *data, size_t len)`，表示函数不能通过 data 修改数据；它不保证其他任务或 DMA 同时不会改这块数据，也不保证异步发送已经结束。

## Q09 指针失效与所有权

“野指针”是工程俗称，通常指未初始化、乱指向或无效的指针；“悬空指针”专指所指对象生命周期已经结束。两者不是 C 标准中互斥的正式分类。

```c
int *p;                  /* 未初始化，不能解引用 */

int *bad_return(void)
{
    int x = 1;
    return &x;           /* 函数返回后 x 生命周期结束：错误示例 */
}
```

```c
int *p = malloc(sizeof *p);
if (p != NULL) {
    int *alias = p;
    *p = 7;
    free(p);
    p = NULL;
    /* alias 仍然悬空，禁止解引用或再次 free。 */
}
```

free 后置 NULL 有价值：能减少同一个指针变量被重复使用或重复释放的风险；`free(NULL)` 没有作用。但这不能修复其他别名、并发读者、链表残留引用。最重要的是**谁拥有对象、谁释放、哪些借用在何时结束**。

只允许 free 动态分配返回的有效基址或 NULL；不能 free 局部数组、静态数组、偏移后的指针，也不能对同一分配释放两次。分配与释放函数要成对，例如普通 `malloc/free`、FreeRTOS `pvPortMalloc/vPortFree` 按各自接口契约配对。

将局部数组地址放入 RTOS 指针队列、异步 SPI DMA 提交后马上复用发送缓冲区，都是指针生命周期错误的常见来源。

## Q12 inline 与宏

```c
#define SQUARE(x) ((x) * (x))

static inline int square_i(int x)
{
    return x * x;  /* 本例假设输入不会导致有符号整数溢出 */
}
```

| 对比     | 宏                | static inline 函数      |
| ------ | ---------------- | --------------------- |
| 发生阶段   | 预处理文本替换          | 编译器按函数语义处理            |
| 类型检查   | 宏本身没有函数参数类型检查    | 有参数类型检查               |
| 参数求值   | 可能重复或不求值         | 每个实参按函数调用语义求值一次       |
| 作用域、调试 | 文本替换容易产生意外       | 有函数作用域，通常更容易调试        |
| 是否展开   | 宏文本被展开，不等于最终没有指令 | 编译器决定是否内联，inline 不是命令 |

`SQUARE(i++)` 展开成 `((i++) * (i++))`，在 C 中存在未排序的重复修改，属于未定义行为，不能回答成某个确定数字。`square_i(i++)` 只对这个实参求值一次。函数不同实参之间的求值顺序仍不可随意假设。

内联可能降低调用开销，也可能导致代码体积增长、指令缓存压力增加。递归、函数过大、优化选项等会影响内联。头文件放小工具函数，C 中常用 `static inline`，可以避免误用 C 的外部 inline 定义规则。[GCC inline 文档](https://gcc.gnu.org/onlinedocs/gcc/Inline.html)

多语句宏需要 `do { ... } while (0)` 包装；寄存器位常量、条件编译仍适合宏。能用普通函数表达的业务逻辑一般优先函数。

## Q15 编译四阶段与头文件

```text
main.c ──预处理──> main.i ──编译──> main.s ──汇编──> main.o ──链接──> firmware.elf
```

| 阶段 | 主要工作 | 常见错误 |
|---|---|---|
| 预处理 | 展开 include/宏，处理条件编译，移除注释 | 头文件找不到、宏污染 |
| 编译 | 词法/语法/语义检查，优化，生成目标汇编 | 类型错误、语法错误 |
| 汇编 | 汇编转机器码，形成目标文件及符号/重定位信息 | 汇编指令不支持 |
| 链接 | 合并目标文件，解析符号，重定位，按链接脚本安排地址 | 未定义引用、重复定义、区域溢出 |

实际驱动工具可能合并阶段；上表是学习时的逻辑分层。ELF 再经 `objcopy` 转成 BIN/HEX，通常不算这四阶段中的独立“编译阶段”。

### 头文件为什么不宜定义共享变量

头文件会被复制到每个包含它的翻译单元里：

```c
/* 错误设计：放在 header.h 中 */
int global_count = 0;
```

两个 `.c` 都 include 它，就各有一个外部定义，链接冲突。正确的共享写法：

```c
/* counter.h */
#ifndef COUNTER_H
#define COUNTER_H
extern int global_count;   /* 声明 */
#endif

/* counter.c：这里只展示内容，不要与头文件拼成一个实际文件 */
#include "counter.h"
int global_count = 0;      /* 唯一定义 */
```

include guard 只防止**同一翻译单元**重复包含，不能阻止不同 `.c` 各定义一个全局符号。

“头文件绝不能定义变量”也不准确：`static` 变量可以定义，但每个翻译单元有自己的副本，通常不是你想要的共享状态；C 中头文件的 `const int table_size = 8;` 仍可能产生外部定义冲突。`int x;` 在文件作用域是暂定定义，部分工具链的 common 合并行为会掩盖错误，不能依赖。

## 自测与答案

1. volatile 能否保护两个任务共同执行 `count++`？
2. static 局部变量能否直接被其他函数用名字访问？
3. `const int *p` 能否改指向？它指向的变量一定不能改吗？
4. free 后把 p 清零，alias 为什么仍然危险？
5. include guard 为什么救不了头文件中的全局定义？
6. `inline` 不展开时是否仍然正确？

> [!answer]- 答案
> 1. 不能；需要同步/原子读改写。2. 不能，名字仍为块作用域。3. 可以改指向；若实际对象可写，可经合法的非 const 路径修改。4. alias 没有被更新，所指对象已死亡。5. 它只防一个翻译单元内重复展开。6. 正确的函数定义/链接安排下仍正确，内联影响优化而非业务语义。
