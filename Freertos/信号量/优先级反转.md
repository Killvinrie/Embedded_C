## 一、什么是优先级反转？

假设 FreeRTOS 中有三个任务：

|任务|优先级|功能|
|---|---|---|
|TaskH|5|姿态控制|
|TaskM|3|通信处理|
|TaskL|1|日志记录|

优先级关系：

\[ P_H>P_M>P_L \]

其中 TaskH 和 TaskL 需要访问同一个共享资源，由互斥量保护。

### 1. 正常执行过程

**时刻 T1：TaskL 获取互斥量。**

```
xSemaphoreTake(xMutex, portMAX_DELAY);

/* 访问共享资源 */
```

此时：

```
CPU：TaskL

Mutex 持有者：TaskL
```

**时刻 T2：TaskH 变为就绪状态。**

由于 TaskH 优先级更高，它抢占 TaskL。

随后执行：

```
xSemaphoreTake(xMutex, portMAX_DELAY);
```

但是 Mutex 被 TaskL 持有。

于是：

```
TaskH → Blocked
```

到这里，高优先级任务等待低优先级任务，本身属于共享资源导致的阻塞。

**时刻 T3：TaskM 变为就绪状态。**

由于：

M优先级> L

TaskM 抢占 TaskL。

问题出现了：

```
TaskH 等待 TaskL 释放 Mutex
                │
                ▼
         TaskL 需要运行
                │
                ▼
         TaskM 抢占 TaskL
                │
                ▼
       TaskH 被间接延迟
```

虽然 TaskM 根本不使用这个 Mutex，但它仍然影响了 TaskH 获取资源的时间。

### 2. 时间线

不采取优先级反转缓解措施时：

```
时间 ─────────────────────────────────────►

TaskH         [等待 Mutex................][运行]
TaskM                    [执行──────────]
TaskL   [持有 Mutex][暂停...............][释放]
```

从 CPU 执行角度：

```
T1        T2        T3                  T4
│         │         │                   │
▼         ▼         ▼                   ▼
TaskL → TaskH → TaskM ───────────→ TaskL → TaskH
          │                          │
          ▼                          ▼
      获取失败                    释放 Mutex
      进入阻塞
```

**关键问题：高优先级 TaskH 的执行进度，间接受到了中优先级 TaskM 的影响。**

如果 TaskM 持续占用 CPU，TaskH 可能被阻塞很长时间。

这就是典型的优先级反转问题。
