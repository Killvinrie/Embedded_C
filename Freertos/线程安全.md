# 一、什么是线程安全（Thread Safety）？

线程安全是 C 语言、Linux 多线程编程以及 FreeRTOS 中非常重要的概念，也是嵌入式软件工程师面试中的高频考点。

我们先从一个简单的问题开始：

**假设两个 FreeRTOS 任务同时操作同一个全局变量，会发生什么？**

```c
int count = 0;

void Task1(void *argument)
{
    while (1)
    {
        count++;
    }
}

void Task2(void *argument)
{
    while (1)
    {
        count++;
    }
}
```

假设 Task1 和 Task2 分别执行 1000 次 `count++`。

你可能认为：

```
最终 count = 2000
```

但实际上，最终结果可能小于 2000。

为什么？

因为 `count++` 通常不是一条不可分割的操作。

## 1.1 count++ 在 CPU 中是如何执行的？

对于下面这条 C 语言语句：

```c
count++;
```

CPU 可能需要执行三个步骤：

```
第一步：从内存中读取 count
第二步：count + 1
第三步：将结果写回内存
```

假设 STM32F411 使用的 ARM Cortex-M4 编译出了类似下面的汇编指令：

```asm
LDR R0, [R1]    ; 读取 count
ADD R0, R0, #1  ; 加一
STR R0, [R1]    ; 写回 count
```

需要强调，这只是为了说明原理的示意汇编，实际指令与编译优化有关。

正常执行：

```
初始 count = 0

Task1:
    读取 count = 0
    执行 +1
    写回 count = 1

Task2:
    读取 count = 1
    执行 +1
    写回 count = 2
```

最终结果为 2。

但是 FreeRTOS 支持任务抢占，如果在执行过程中发生任务切换，结果就不一定正确。

### 情况：发生任务抢占

```
时间 →
───────────────────────────────────────

Task1                  Task2
  │                      │
  │ 读取 count = 0       │
  │                      │
  │ count + 1 = 1        │
  │                      │
  │  被抢占              │
  │ ───────────────────► │
  │                      │ 读取 count = 0
  │                      │
  │                      │ count + 1 = 1
  │                      │
  │                      │ 写回 count = 1
  │ ◄─────────────────── │
  │                      │
  │ 写回 count = 1       │
  │                      │
  ▼                      ▼

最终 count = 1
```

两个任务明明各自执行了一次加一操作，最终结果却是 1。

这就是典型的**竞态条件（Race Condition）**。

在 C 语言的并发内存模型中，如果两个线程没有适当同步地访问同一非原子对象，且至少一个访问是写操作，就可能产生数据竞争（Data Race），在标准 C 线程模型下属于未定义行为。

# [[临界区]]和[[互斥锁]]有什么区别？

==这是一个非常经典的面试问题。==

| 比较项目     | 临界区                    | 互斥锁                |
| -------- | ---------------------- | ------------------ |
| 典型接口     | `taskENTER_CRITICAL()` | `xSemaphoreTake()` |
| 实现思路     | 屏蔽特定中断，防止任务抢占          | 控制资源访问权限           |
| 任务能否阻塞等待 | 不允许                    | 可以                 |
| 对中断响应的影响 | 可能增加中断延迟               | 一般不需要屏蔽中断来持锁       |
| 优先级继承    | 不涉及                    | 支持                 |
| 适用场景     | 极短的共享数据操作              | 多任务共享外设或数据         |
| 使用限制     | 临界区必须尽量短               | 需要考虑锁等待、死锁等问题      |

**一般原则：**

对于极短的共享数据更新，可以使用临界区。

对于需要较长时间保护的共享资源，可以考虑互斥锁。

但如果涉及高频姿态控制、ISR 或 DMA，还应根据实时性要求考虑队列、任务通知、双缓冲或原子操作。

##  FreeRTOS 怎么解决？

以 FreeRTOS 的 `heap_4.c` 为例。

其内存分配函数使用调度器挂起机制保护关键的堆管理操作。

原理可以简化为：

```c
void *pvPortMalloc(size_t xWantedSize)
{
    void *pvReturn = NULL;

    vTaskSuspendAll();

    {
        // 查找空闲内存块
        // 修改空闲链表
        // 必要时分割内存块
        // 更新堆管理信息
    }

    xTaskResumeAll();

    return pvReturn;
}
```

其中[[vTaskSuspendAll]]函数挂起任务调度器，阻止普通任务切换
